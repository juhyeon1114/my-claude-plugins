# 1. 절대 규칙
- GitHub에 아무것도 쓰지 않는다. 제목과 본문은 '나'에게 채팅으로만 보여준다.
- 금지: `gh pr edit`, `gh pr create`, `gh pr comment`, `gh api` 의 쓰기 요청.
- 허용: `gh pr view`, `gh pr diff`, `gh pr list` 같은 읽기 명령과 로컬 `git` 읽기 명령.
- 제목과 본문은 각각 마크다운 코드블록 하나에 담아 출력한다. 사용자가 그대로 복사해서 붙일 수 있어야 한다.

# 2. 제목 작성 규칙
- 제목은 하나만 제안한다.
- `~/.claude/commit-message.md`가 있으면 그 규칙을 따른다.
- 없으면 `<type>: <description>` 형식으로 쓴다.
  - type은 feat, fix, docs, style, refactor, perf, test, chore, build, ci 중 하나다.
  - description은 한국어로 50자 안에서 쓰고, 파일과 함수 같은 실제 이름은 원문 그대로 넣는다.

# 3. 본문 작성 규칙
- 작업 브랜치와 대상 브랜치를 확인한다. 스택형 PR이면 비교 기준이 main이 아니다.
- 프로젝트에 PR Template이 있는지 확인하고, 있으면 그 형식을 따른다.
  - 템플릿 섹션이나 체크리스트 항목이 이 PR과 상관없으면 지우지 않고 "없음"으로 둔다.
- 템플릿이 없으면 아래 형식으로 쓴다.
  - "리뷰 시 참고"에는 영향 범위나 주의할 점처럼 리뷰어가 알아야 할 사실만 쓴다. 쓸 내용이 없으면 섹션을 뺀다.
```markdown
## 배경
## 변경 사항
## 리뷰 시 참고
```
- 실제 diff를 읽고 쓴다. 커밋 메시지나 기존 본문만 보고 옮겨 적지 않는다.
- 배경(왜 바꿨는지)은 커밋 메시지, 기존 본문, 브랜치 이름의 티켓 번호로 확인한다.
  그래도 모르면 지어내지 말고 `<!-- TODO: 배경 -->`으로 비워 두고, 비운 자리를 '나'에게 알려준다.
- 변경 사항은 파일별로 나열하지 않고, 같은 목적의 변경을 한 줄로 묶는다.
- PR에 이미 본문이 있으면 사람이 직접 넣은 이미지, 링크, 티켓 링크는 그대로 남긴다.
- 장황하지 않고 중요한 내용만 간결하고 직관적으로 쓴다. `~/.claude/output-styles/korean-plain.md`가 있으면 그 어투를 따른다.
- 다른 MCP는 쓰지 않는다.

# 4. 본문에 쓰지 않는 것
- PR 자체에 관한 메타 정보. 브랜치 이름, 대상 브랜치, 스택형 여부, 커밋 개수, diff 크기.
- 리뷰 방법이나 머지 순서 같은 절차 안내.
- diff에 없는 추측. 후속 작업 계획이나 앞으로 할 일.
