# 버그 리포트

다른 사람이 문제를 똑같이 다시 일으켜 볼 수 있게 알리는 문서다.
고치는 사람이 문제를 재현하지 못하면 고칠 수도 없다. 그래서 재현 절차가 가장 중요하다.

## 구성

1. 제목: 어디서 무엇이 잘못되는지 한 문장으로 쓴다.
2. 심각도와 영향: 얼마나 급한지, 누가 어떤 피해를 보는지 쓴다. 고치는 순서를 정할 때 쓴다.
3. 환경: 문제가 생긴 서버, 버전, 설정을 쓴다.
4. 재현 절차: 문제를 다시 일으키는 순서를 번호를 붙여 쓴다. 누가 해도 같은 결과가 나오게, 조건에 따라 달라지는 단계 없이 쓴다.
5. 기대한 결과: 원래 어떻게 되어야 하는지 쓴다.
6. 실제 결과: 실제로 어떻게 됐는지 쓴다. 몇 번 해서 몇 번 생기는지, 어떤 조건에서는 생기지 않는지도 쓴다.
7. 참고 자료: 로그, 화면, 관련 주문 번호 등을 붙인다.

기대한 결과와 실제 결과를 짝지어 쓰면, 무엇이 잘못인지 따로 설명하지 않아도 드러난다.

## 자주 하는 실수

- "가끔 안 된다"처럼 빈도와 조건 없이 쓴다.
- 재현 절차에 "적당히 기다린다"처럼 사람마다 다르게 따라 할 단계를 넣는다.
- 원인 추측을 사실처럼 쓴다. 추측은 로그 같은 근거와 함께 참고 자료에 둔다.
