# 조사 보고서 예시

## 주문 수집이 10분 안에 끝나지 않는 이유 조사

### 요약

한 번 수집하는 12분 가운데 11분 30초는 쇼핑몰 응답을 기다리는 시간이다. 우리 서버가 일하는 시간은 30초뿐이다.
쇼핑몰을 한 곳씩 차례로 호출하기 때문에 기다리는 시간이 그대로 쌓인다.
쇼핑몰을 동시에 호출하면 수집 시간을 크게 줄일 수 있을 것으로 보인다.

### 목적과 범위

- 한 번 수집에 걸리는 12분이 어디에 쓰이는지 알아낸다.
- 주문 수집 코드와 운영 로그만 봤다. 창고 시스템으로 주문을 넘기는 부분은 보지 않았다.
- 수집 시간을 줄이는 방법을 실제로 시험하는 것은 이번 범위가 아니다.

### 방법

- 9월 8일부터 14일까지 7일 동안의 운영 로그에 남은 수집 1,008번 전체에서, 쇼핑몰 호출마다 시작 시각과 끝 시각을 뽑았다.
- 주문 수집 코드를 읽고 쇼핑몰을 어떤 순서로 호출하는지 확인했다.
- 쇼핑몰 40곳의 호출 제한 규칙을 문서로 확인하려 했지만, 문서를 찾은 곳은 28곳뿐이다.

### 발견 사항

1. 한 번 수집에 평균 12분이 걸린다. 기준인 10분 주기보다 2분 길다. 쇼핑몰 응답을 기다리는 시간이 11분 30초, 주문 저장과 그 밖의 일이 30초다.
   - 근거: 운영 로그 분석 결과 (첨부 1)
2. 코드는 쇼핑몰 40곳을 한 곳씩 차례로 호출한다. 한 곳의 응답을 받아야 다음 곳을 호출한다.
   - 근거: `OrderCollectJob` 클래스의 `collectAll` 메서드
3. 가장 느린 쇼핑몰 한 곳은 응답을 다 받는 데 평균 1분 30초가 걸린다. 가장 느린 3곳을 합치면 4분이다.
   - 근거: 첨부 1의 쇼핑몰별 응답 시간 표
4. 문서를 찾은 28곳은 모두 1초에 5번 이상의 호출을 허용한다.
   - 근거: 쇼핑몰별 API 문서 목록 (첨부 2)

### 해석과 제안

- 수집이 느린 까닭은 우리 서버가 느려서가 아니라 기다리는 시간이 쌓여서다.
- 쇼핑몰을 동시에 호출하면 기다리는 시간이 겹쳐서 전체 시간이 줄어든다.
- 다만 아무리 많이 동시에 호출해도, 가장 느린 쇼핑몰 한 곳의 시간인 1분 30초보다 짧아지지는 않는다.
- 동시 호출 수를 1곳, 4곳, 8곳, 16곳으로 바꿔 가며 검증 서버에서 실험해 보기를 제안한다.
- 문서를 찾지 못한 12곳은 실험할 때 거절 응답이 오는지 따로 지켜본다.
