# 런북 예시

## 주문 수집이 멈췄을 때

마지막 수정: 2026년 9월 21일, 김주현
관련 문서: 주문 수집 지연 장애 회고 (2026년 9월 15일)

### 여는 때

- 알림 `order-collect-stuck`이 왔다. 주문 수집이 시작하고 15분이 지나도 끝나지 않았다는 뜻이다.
- 고객사에서 주문이 들어오지 않는다는 문의가 왔다.

### 영향

- 수집이 멈춘 동안 모든 쇼핑몰의 주문이 들어오지 않는다.
- 쇼핑몰은 지난 24시간의 주문만 다시 조회할 수 있게 해 준다. 24시간 안에 복구하지 못하면 주문을 잃는다.
- 알림을 받으면 30분 안에 조치를 시작한다.

### 먼저 확인할 것

1. 지금 돌고 있는 수집 목록을 본다.
   ```bash
   curl -s "https://admin.internal/order-collect/runs?status=RUNNING"
   ```
2. 결과에 따라 다음으로 간다.
    - 수집이 두 개 이상이다: 두 수집이 서로 기다리는 상태일 가능성이 높다. 조치 A로 간다.
    - 수집이 하나이고, 쇼핑몰 한 곳의 호출에서 멈춰 있다: 조치 B로 간다.
    - 수집이 하나도 없다: 수집 스케줄러가 멈춘 것이다. 도움 요청으로 간다.

### 조치 A: 서로 기다리는 수집을 끝낸다

1. 늦게 시작한 수집부터 끝낸다. `{runId}`에는 확인 1에서 본 수집 번호를 넣는다.
   ```bash
   curl -X POST "https://admin.internal/order-collect/runs/{runId}/stop"
   ```
2. 1분 기다린 뒤 확인 1을 다시 실행한다. 남은 수집도 끝나지 않았으면 같은 방법으로 끝낸다.
3. 멈춘 동안 들어오지 않은 주문을 다시 모은다. `{from}`에는 멈춘 수집이 시작한 시각을 넣는다.
   ```bash
   curl -X POST "https://admin.internal/order-collect/recollect?from={from}"
   ```

수집을 강제로 끝내도 주문은 사라지지 않는다. 저장하지 못한 주문은 3단계에서 다시 모으고, 이미 저장한 주문은 쇼핑몰 주문 번호로 중복 저장을 막는다.

### 조치 B: 멈춘 쇼핑몰 한 곳을 수집에서 잠시 뺀다

1. 멈춘 쇼핑몰을 수집 대상에서 뺀다. `{mallId}`에는 확인 1에서 본 쇼핑몰 번호를 넣는다.
   ```bash
   curl -X POST "https://admin.internal/order-collect/malls/{mallId}/pause"
   ```
2. 그 쇼핑몰의 개발자 공지 페이지에서 장애 공지가 있는지 본다.
3. 쇼핑몰이 정상으로 돌아오면 수집 대상에 다시 넣는다.
   ```bash
   curl -X POST "https://admin.internal/order-collect/malls/{mallId}/resume"
   ```

### 끝났는지 확인하는 방법

- 다음 주기의 수집이 10분 안에 끝난다.
- 대시보드 "주문 수집"의 "마지막 수집 완료 시각"이 지금부터 10분 안이다.
- 조치 A를 했다면, 다시 모으기 결과에 실패한 쇼핑몰이 없다.

### 되돌리는 방법

- 조치 A로 끝낸 수집은 되돌릴 수 없다. 대신 다시 모으기로 빠진 주문을 채운다.
- 조치 B로 뺀 쇼핑몰은 `resume`으로 다시 넣는다. 빼 둔 쇼핑몰은 대시보드의 "일시 중지된 쇼핑몰"에서 확인한다.
- 병렬 수집을 적용한 뒤에 생긴 문제로 보이면 설정값 `order.collect.concurrency`를 1로 바꾼다. 예전처럼 한 곳씩 차례로 수집한다.

### 도움 요청

- 조치를 시작하고 30분이 지나도 정상으로 돌아오지 않으면 연락한다.
- 먼저 주문팀 당번에게 연락한다. 슬랙 `#order-oncall` 채널에 이 문서 링크와 확인 1의 결과를 붙인다.
- 당번이 15분 안에 답하지 않으면 주문팀 팀장에게 전화한다.
