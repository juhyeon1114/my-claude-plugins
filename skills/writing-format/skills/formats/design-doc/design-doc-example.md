# 설계 문서 예시

## 주문 수집 병렬 처리 설계

작성자: 김주현
검토자: 주문팀 전원
상태: 검토 중

### 배경

주문 수집은 10분마다 연동 쇼핑몰 40곳을 차례로 호출한다. 한 번 수집에 12분이 걸려서 10분 주기를 지키지 못한다.
연동 쇼핑몰은 매달 3곳 정도씩 늘고 있다.

### 목표

- 한 번 수집을 5분 안에 끝낸다.
- 연동 쇼핑몰이 100곳이 되어도 10분 주기를 지킨다.
- 문제가 생기면 배포 없이 예전 방식으로 되돌릴 수 있게 한다.

### 목표가 아닌 것

- 쇼핑몰마다 다른 호출 제한 규칙을 맞추는 일은 이번에 하지 않는다.
- 수집한 주문을 저장하는 방식은 바꾸지 않는다.

### 제안

작업 대기열에 쇼핑몰 40곳을 넣고, 일꾼 4개가 대기열에서 쇼핑몰을 하나씩 꺼내 수집한다.
일꾼 하나가 수집을 마치면 대기열에서 다음 쇼핑몰을 꺼낸다.
일꾼 수는 설정값 `order.collect.concurrency`로 정하고, 기본값은 4다. 이 값을 1로 바꾸면 예전 방식과 같아진다.
쇼핑몰이 호출을 거절하면 그 쇼핑몰을 30초 뒤에 대기열에 다시 넣는다. 세 번 거절당하면 이번 주기에서는 건너뛰고 알림을 보낸다.

### 검토한 다른 방안

| 방안                                      | 고르지 않은 이유                                                  |
|-------------------------------------------|-------------------------------------------------------------------|
| 수집 주기를 15분으로 늘린다               | 고객사에 약속한 10분을 어기게 된다                                |
| 쇼핑몰마다 동시 호출 수를 따로 정한다     | 호출 제한 규칙을 확인하지 못한 쇼핑몰이 12곳이라 정할 근거가 없다 |
| 스레드 하나에서 비동기 호출로 모두 부른다 | 쇼핑몰 연동 모듈 40개를 모두 고쳐야 해서 개발에 3주가 걸린다      |
| 쇼핑몰이 주문을 알려 주는 방식으로 바꾼다 | 이 방식을 지원하는 쇼핑몰이 40곳 가운데 6곳뿐이다                 |

### 위험과 대응

- 같은 쇼핑몰을 한 주기에 두 번 수집할 수 있다. 일꾼 여럿이 대기열을 함께 쓰기 때문이다. 대기열에서 꺼낸 쇼핑몰은 "수집 중"으로 표시하고, 다시 넣을 때 이 표시를 확인한다. 주문은 쇼핑몰의 주문 번호로 중복 저장을 막는다.
- 쇼핑몰이 호출을 거절할 수 있다. 실험에서는 4곳까지 거절이 없었다. 거절되면 다시 시도하고, 계속 거절되면 알림을 보낸다.
- 데이터베이스 부하가 순간적으로 커질 수 있다. 적용 첫 주에는 데이터베이스 부하를 매일 확인한다.

### 운영 고려 사항

모니터링과 알림

- 한 번 수집에 걸린 시간과 쇼핑몰마다 걸린 시간을 기록한다. 대시보드 "주문 수집"에서 본다.
- 수집 시간이 8분을 넘으면 경고를 보낸다. 15분이 지나도 끝나지 않으면 알림 `order-collect-stuck`을 보낸다.
- 알림에는 대응 순서를 적은 런북 "주문 수집이 멈췄을 때"의 링크를 넣는다.
- 쇼핑몰이 호출을 거절한 횟수를 쇼핑몰마다 센다.

보안

- 새로 여는 외부 접속은 없다.
- 쇼핑몰 계정 정보는 지금처럼 비밀 값 저장소에서 읽는다. 일꾼마다 따로 복사해 두지 않는다.

개인정보

- 수집한 주문에는 받는 사람의 이름, 전화번호, 주소가 담긴다.
- 일꾼이 여럿이 되면서 로그가 늘어난다. 로그에는 쇼핑몰 이름과 주문 번호만 남기고, 받는 사람 정보는 남기지 않는다.

### 열린 질문

- 기본값 4가 알맞은가? 실험에서 8곳은 조금 더 빨랐지만 거절이 3건 있었다.
- 세 번 거절당한 쇼핑몰을 건너뛰면 그 주문은 10분 늦게 들어온다. 이 정도 지연을 받아들일 수 있는가?
